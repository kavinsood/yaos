# Body residency accounting

Status: implemented measurement contract for RFC 08. Admission priority,
backpressure, connection budgets, and mobile cooling remain RFC 09 policy.

## Claim boundary

`yaos-body-residency-v1` produces a heuristic resident-cost estimate. It is not
a JavaScript heap measurement, process RSS, mobile free-memory reading, or proof
that the runtime can allocate the same number of additional bytes.

The existing 48 MiB client limit now bounds the sum of loaded-body resident
estimates. It does not include temporary reservations or shared root/catalog
resources. Diagnostics report those alongside the budget rather than silently
calling all of them “memory.” This keeps the historical safety limit working
while making its scope reviewable before RFC 09 changes enforcement.

## Evidence and estimates

Each loaded body records exact observations where the runtime exposes them:

- full encoded Yjs state byte length;
- materialized Markdown UTF-16 code units and UTF-8 bytes;
- Yjs struct, deleted-struct, and client-bucket counts;
- Yjs pending-struct and pending-delete-set update byte lengths;
- externally reported local/remote pending-buffer byte lengths;
- externally reported provider, socket, and awareness-peer counts.

The encoded state is a serialization-size proxy. A `Y.Doc` does not normally
retain that freshly generated byte array. Struct counts characterize fragmented
history but expose no supported byte-size API. Materialized text can share or
retain engine storage in ways YAOS cannot observe. These values therefore feed
an explicitly versioned heuristic:

```text
resident estimate =
    encoded state proxy
  + 2 bytes per materialized UTF-16 code unit
  + 96 bytes per Yjs struct
  + 24 additional bytes per deleted struct
  + 64 bytes per Yjs client bucket
  + exact reported pending-buffer bytes
  + 8 KiB per provider
  + 16 KiB per socket
  + 256 bytes per awareness peer
  + 512 bytes of body metadata
```

The constants are conservative engineering coefficients, not benchmark results.
Changing one requires a new estimator version and before/after calibration data.
Callers may inject a runtime-specific cost function; component observations stay
available even when that function replaces the default total.

## Scratch and shared resources

Body load, server replacement, server merge reconstruction, and persistence
encoding create temporary reservations before allocating or encoding where the
input size is known. A public idempotent reservation API covers diff3, recovery,
and later format adapters. Reservations record owner, kind, age, and estimated
bytes and contribute to the accounted high-water mark.

RFC 09 can ask for a cold-load estimate using only the stored encoded byte
length. It returns separate projected resident, reconstruction scratch, and
peak-additional values without decoding a second document. The estimate is
deliberately coarse because encoded bytes cannot reveal decoded text size or
fragmented struct history; the manager remeasures after the single real decode.
Loaded body IDs and per-body observations are returned as defensive plain values.

Shared reporting accepts root/catalog bytes, shared pending buffers, the root
provider/socket, and root awareness peers. Per-body reporting accepts candidate
or transport buffers and body provider/socket/awareness counts. Resource owners
must clear their report when ownership ends. Missing reports remain zero and the
diagnostic caveat says so; zero never claims that the resource is free.

The current product adapter still needs to wire these owner reports:

- `VaultSync` should update per-body signals when a session, candidate buffer,
  provider, socket, or awareness state changes;
- `VaultSync` should report root encoded/catalog size, root pending updates, and
  its root transport through `setSharedResourceSignals`;
- the telemetry adapter should expose `bodies.residencySnapshot()` through the
  optional read-only diagnostics port.

Those seams deliberately contain no admission policy and can be connected
without changing the estimator.

## Diagnostics

`BodyManager.residencySnapshot()` returns plain values only. It includes:

- resident, temporary, shared, and combined accounted estimates;
- current and high-water loaded-body counts and byte estimates;
- cold, joined, and cache-hit load counts plus a bounded latency distribution;
- completed and blocked eviction attempts;
- blocker observations and current blockers per loaded body;
- p50/p95 distributions for resident estimate, encoded size, struct count, and
  structs per thousand text code units;
- active temporary reservations and all estimator caveats.

Eviction blockers are explicit: dirty state, unsettled candidates, pending local
updates, pins, leases, projection ownership, non-clean synchronization, and a
quiescing/disposed runtime. Multiple reasons may apply to one body.

The diagnostics bundle has an optional body-residency field. Until the product
adapter connects it, exports contain `null`, which is evidence of unavailable
instrumentation rather than an invented zero.

## Calibration protocol

Before RFC 09 changes a limit or adds pressure behavior, collect the same fixture
families on desktop Obsidian, iOS, Android, and the Node daemon:

1. small clean notes at increasing body counts;
2. large clean notes at increasing text sizes;
3. compact and heavily edited documents with equal final text;
4. many dirty, pinned, leased, and durably pending bodies;
5. rapid editor switching with provider/socket churn;
6. concurrent bootstrap reconstruction and three-way merges.

For runtimes exposing heap/RSS evidence, sample before load, after quiescence,
and after eviction/GC opportunity. Compare deltas to estimator components; do
not fit against a single warm process. Mobile measurements must also record
foreground/background state and OS memory-pressure termination separately.

Worker server cache limits are a separate runtime scope. They require equivalent
server-side measurements and must not inherit client coefficients merely because
both store Yjs documents.

## RFC 09 handoff

RFC 09 may use these observations to choose admission, cooling, wake priority,
and connection limits. It should decide explicitly whether temporary/shared
estimates join the enforced budget, how much scratch headroom is reserved, and
what backpressure outcome is returned when every resident body is blocked.
