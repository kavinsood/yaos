# Client e2e (real relay)

- `onboard.ts`: `onboardVault(baseUrl, { devices, label })` creates a fresh vault with N enrolled devices. It claims an unclaimed server, or uses operator login with the key in `LOG_DIR/client-e2e-context-<host>.json` (mode 0600). `pairDevice(vault, name)` adds one more device; `revokeDevice(vault, deviceId)` revokes one from the console. Device tokens are secrets: pass them only to adapters, and log through `redact()`.
- `nodeXhr.ts`: `nodeXhr`, an XMLHttpRequest over node:http(s) with only what httpBlob's PUT uses (Node has none, and httpBlob has no fetch fallback for PUT). Every node caller of `createHttpBlob` / `probeHttpBlob` that puts passes `xhr: nodeXhr`.
- `smoke.ts`: the WP-C RelayPort adapter (`wsRelay.ts` / `relayHttp.ts`) against a live relay with two devices. It writes `LOG_DIR/client-e2e-wpc-smoke-<label>-<stamp>.json` and exits 1 on failure.
- `engines.ts` (+ `engineKit.ts`): three headless `LogEngine`s on the production adapters (wsRelay, idbStorage on fake-indexeddb, suite-0 crypto, httpBlob) syncing through the relay. It covers create and edit, keystroke-to-peer latency, concurrent edits, rename and delete, offline edits with reconnect, a large update through the blob store (only a small bodyUpdateRef rides the log), relay checkpoints, fresh-device catch-up, restart from IndexedDB, IndexedDB loss followed by mirror recovery, and, with `--relay-restart` (local only), a relay process restart. It writes `LOG_DIR/client-e2e-wpc-engines-<label>-<stamp>.json`.
- `fullClients.ts` (+ `fullKit.ts`, `fullCheck.ts`, `fullScenarios1.ts`, `fullScenarios2.ts`, `fullLatency.ts`, `wireTap.ts`): 3-4 full clients (host runtime, simulated Obsidian vault/workspace/config dir, the real engine on the production ports) through the relay. It uses the relay's R2 store. It writes `LOG_DIR/client-e2e-full-<label>-<stamp>.json`. Latency metrics, in ms:
  - `lone_*` (E2EE on, suite 1) and `lone_plain_*` (suite 0), each on its own vault: one edit at a time. Before each edit the clients are converged and the relay has had no commit for longer than `groupCommit.quietMs` from VAULT_READY, plus 100 ms. A lone edit therefore takes the relay's leading-edge commit. Each per-peer sample is split at its critical frame (the last of the sender's frames the peer needed) into `_sender_ms` (local change to that frame's APPEND), `_relay_ms` (APPEND to its COMMITTED / COMMIT_NOTICE on the peer, or PROVISIONAL for an open editor) and `_receiver_ms` (to bytes on the peer's disk or in its view). The rows are in `extra.<prefix>_samples`.
  - `sustained_*` (suite 0, the scenario vault): back-to-back edits, each started as soon as the previous one reached every peer. They pay the relay's minimum commit interval per commit. `extra.sustainedFloorMsPerCommit` holds that interval.
  - `wireTap.ts` takes its timestamps in the harness: the NetSwitch session wrapper (APPEND, receipts, COMMITTED, PROVISIONAL), a WebSocket wrapper (VAULT_READY limits) and SimVault's `onMutation` (engine disk writes).
- `snapshots.ts`: snapshot backup (DESIGN §j.4) with two full clients. It uses the relay's attachment storage (R2, on by default in `start-local.sh`). Device a uploads a 2-part snapshot, a fresh device b lists, verifies and restores it (its files match, and the restore syncs back), then a byte of a second snapshot's part is flipped at rest in the local R2 store (`--state-dir`, the relay's persist dir) and b must refuse it with `content_corrupt`. It writes `LOG_DIR/client-e2e-snapshots-<label>-<stamp>.json`.
- `e2ee.ts`: suite 1 (end-to-end encrypted) through the real plugin controller (`FullClient.runtimeFor`), so main's pin and key flow runs as in production. It uses the relay's R2 store. a enables encryption (genesis, pin, restart) and seals a note and an attachment; b installs the key by recovery key and c by QR; the relay's state dir holds no plaintext; a console revoke plus a re-key shuts b's gate until it installs K_2; d enrolls after the roll (K_1 via the prevWrap chain) and its blob GC deletes a planted orphan only once its gate is open; a final scan finds no key or recovery key outside SecretStorage (diagnostics bundles, data.json, IndexedDB, logs, the relay's state and log, the results file). It writes `LOG_DIR/client-e2e-e2ee-<label>-<stamp>.json`.
- `typingDuringUpload.ts` (+ `fullWorker.ts`): typing stays smooth on the UI thread while an attachment of the largest size the blob store takes uploads. Device a runs as on desktop: its host (bound editor, BindingManager, vault) on the main thread and its engine on a `worker_threads` Worker (`FullClient` option `carrier: "worker"`, which runs `fullWorker.ts`: `createEngine` with carrier `"worker"` over `createWorkerEngineTransport`, on the same production ports). Device b, a full client on the worker carrier with the note open in a bound editor, runs in a child process. On a fresh vault, E2EE off (suite 0) and on (suite 1, through the plugin controller as in `e2ee.ts`), a types `--rate` keys/s (one editor transaction per key) for a `--baseline-s` baseline, then an attachment appears on its disk and it keeps typing until b has it. The size is derived as the engine derives it: the relay's `maxBlobUploadBytes` (`httpBlob.ts` `probeHttpBlob`, `limits.ts` `MAX_BLOB_UPLOAD_BYTES` when none is named), less the sealing overhead under suite 1 (`maxSealedBlobPlaintext`), and it must equal a's status `maxBlobBytes`. Per window it records, in ms:
  - a's main thread: `monitorEventLoopDelay({ resolution: 1 })` p50/p99/max, the longest gap of a 1 ms heartbeat, and each key's synchronous dispatch (its editor transaction plus the BindingManager flush that posted it, timed through an own-property wrapper of `flushSlot`); the engine threads' loop stats (diagnostic);
  - key -> peer, from the key's scheduled press to the key in b's view, split at the first body APPEND on a's socket after its flush (`sender`), that frame's PROVISIONAL / COMMITTED as b's engine thread handles it (`relay`: a blocked b engine shows here; the timelines tell them apart) and b's view (`receiver`);
  - the upload's phases (a's reads, its PUT, b's GET, b's write), its wall time, peak RSS of each process, and every post of an attachment-sized buffer between a main thread and its engine thread, moved (detached after the post) or copied.
  Clocks are `absNow()` on each thread; b's and the engine threads' are calibrated by the round trip with the least delay. Gates (exit 1, the numbers are written either way), upload window: a's event-loop delay max <= 50 ms, dispatch p99 <= 16 ms, key -> peer p50 <= the baseline's + 100 ms, no key over 1 s (each stall's frame timeline is in `extra.<vault>.stalls`); b's attachment sha256-identical; both views and disks hold the header plus every typed key, in order. It writes `LOG_DIR/client-e2e-typing-<label>-<stamp>.json`.
- `snapshotMemory.ts`: peak memory of the streaming snapshot export and verification on a generated vault (no relay).
- `tsconfig.json`: `npx tsc -p e2e/client/tsconfig.json` typechecks these scripts. They are not part of `typecheck:client`.

LOG_DIR defaults to `/Users/kavin/personal/obsidiansync/experiments/logs`. Override it with `YAOS_E2E_LOG_DIR`.

Attachments, updates above `MAX_INLINE_UPDATE_BYTES` and snapshot parts go to the relay's blob store (R2) over HTTP PUT; they never ride the relay's sequence log (DESIGN §j.1). `start-local.sh` binds a local emulated R2 bucket by default, on every start, including the mid-run restarts of `fullClients.ts` and `engines.ts --relay-restart` (`--r2` is accepted and does nothing). `--no-r2` starts a relay without a store, on which clients do not sync attachments (fail closed); no suite here needs it. The deployed e2e worker (`deploy.sh`) binds a real R2 bucket, the test bucket `yaos-relay2-e2e` (`config.sh` rewrites the `bucket_name` of every `yaos-relay2-*` config, local ones included; never `yaos`, the legacy production bucket), so `--host https://<worker>.kavinsood.workers.dev` runs these suites against it; the operator key comes from that host's context file. `e2ee.ts` scans the relay's state dir at rest, which only a local relay has: pass `--state-dir` an empty directory for a deployed host (that check then covers nothing).

```sh
URL=$(zsh scripts/relay-dev/start-local.sh --fresh | tail -1)
node --import jiti/register e2e/client/smoke.ts --host "$URL" --label local
node --import jiti/register e2e/client/engines.ts --host "$URL" --label local --relay-restart
zsh scripts/relay-dev/stop-local.sh   # always

URL=$(zsh scripts/relay-dev/start-local.sh --fresh --port 8796 | tail -1)
node --import jiti/register e2e/client/snapshots.ts --host "$URL" --label local
node --import jiti/register e2e/client/e2ee.ts --host "$URL" --label local
zsh scripts/relay-dev/stop-local.sh --port 8796

URL=$(zsh scripts/relay-dev/start-local.sh --fresh --port 8809 | tail -1)
node --import jiti/register e2e/client/typingDuringUpload.ts --host "$URL" --label local --vault both
zsh scripts/relay-dev/stop-local.sh --port 8809
```
