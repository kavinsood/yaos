# §5.3 socket ack as receipt: harness prototype

Status: prototype in the harness only. `src/sync/vaultSync.ts` is unchanged. The code is `scripts/relay2/lib/socketReceipts.ts`, driven by `scripts/relay2/l5-cli-baseline.ts --mode relay|relay250 [--offline-probe]`, plus the B6 scenario in `scenarios/behaviour.ts`. The server contract is `docs/relay2-protocol.md` (envelope pairing, candidate dedupe, BODY_COMMITTED echo).

## 1. Can the socket wrapper link a frame to VaultSync's own candidate? No.

Every frame the real provider sends goes through this chain:
`YSyncProvider._updateHandler` → `FencedWebSocket.send` → `VaultSyncOptions.webSocket#send`.

A `ws` subclass passed as `webSocket` sees every binary frame, so it can derive every required envelope field from the frame and the socket:

- `bodyId` comes from `/ws/body/<id>`.
- `payloadDigest` is sha256 of the inner update.
- `clientFrameId` is generated by the wrapper.

It cannot know the candidate that VaultSync creates for the same edit:

- **Timing.** `_updateHandler` sends the frame synchronously from the doc `update` event. VaultSync's observer only queues `pendingUpdates` and schedules `flushBodyCandidate` 250 ms later (maxWait 2 s). When the frame leaves, the candidate does not exist yet.
- **Shape.** The candidate is `Y.mergeUpdates(pendingUpdates)` over every local update in the debounce window. Its `candidateId` is a fresh `crypto.randomUUID()`, so there is no 1:1 mapping from frames to candidates. Its digest, `sha256(candidateDigestMaterial([merged]))`, differs from any single frame's digest unless the window held exactly one update.
- **Access.** The candidate is private runtime state: `pendingCandidates` inside VaultSync. The only outward signal is the `serverReceiptCandidateCaptured` product event, and it fires after the frame was sent.

So, as the round-2 brief allows, the receipt client is implemented in the harness beside the real provider.

## 2. What is real and what is emulated

| Piece | Real or emulated |
|---|---|
| VaultSync runtime, y-partyserver provider, fenced socket, tickets, bootstrap, HTTP requester | **Real.** Unmodified `VaultSync.create` with its default provider factory, as in L5 base. |
| Editor edit | **Real:** `acquireEditorBody` + `completeEditorBodyBinding`, then local `Y.Text` inserts. |
| Frames on the wire | **Real provider frames.** The wrapper adds one `__YPS:` text frame immediately before each non-empty step2/update. With `relay250` it replaces a debounce window's update frames with one merged update frame (`Y.mergeUpdates`, the same function VaultSync uses). |
| Candidate record | **Real store, real digest, emulated capture.** A `StoredBodyCandidate` is written through the real `NodeVaultDatabase.putCandidate` (CLI SQLite, WAL, synchronous=FULL), with `candidateDigest = sha256(candidateDigestMaterial([inner]))` from `server/src/shared/candidateDigest.ts`. Emulated fields: `previousBaseline` is `""`, `capturedLocalUpdates` is 0 and `authority` is omitted. The harness does not track the durable baseline or the local-update count as VaultSync's `bodies` manager does. |
| Persist-before-send | **Emulated ordering** (`persist: "before-send"`, the default). A per-socket promise queue sends envelope + frame only after `putCandidate` resolves, and keeps the provider's frame order (step1, awareness and text frames queue behind it). This matches the durability order of the HTTP path, where the candidate is persisted before submit. `--persist after-send` sends immediately and settles after the put. |
| Settlement | **Real store call.** On the origin `BODY_COMMITTED` (`relay:true`, no `peer`, matching `clientFrameId`), the wrapper checks that `candidateId`, `candidateDigest` and `payloadDigest` equal what it sent. It builds `{vaultId, vaultGeneration, bodyId, bodyEpoch, clientId: deviceId, candidateId, candidateDigest, durableGeneration, runtimeEpoch: commitRuntimeEpoch ?? runtimeEpoch}` and calls `NodeVaultDatabase.confirmPendingCandidate`. That is the same call `completeCandidateSubmission` makes after an HTTP receipt: it checks identity against the stored row, bumps `documents.generation`, recomputes `dirty` and deletes the row. The VaultSync steps around that call are **not** run here: `awaitBodyPersistence`, the `validateReceipt` field checks (re-done inline in reduced form), `markSettled`/residency and product events. |
| HTTP fallback | **Real.** VaultSync's own candidate debounce is parked at 10 min in the relay modes. Unsettled wrapper rows stay in the real store, which `restoreCandidates()` lists and resubmits over HTTP on the next start. Cross-path dedupe was verified live (B6, below). Note: the parked VaultSync candidate is not captured at `destroy()` in this harness ("body coordinator is not accepting work"). A real integration must replace the debounce, not park it. |

## 3. Empirical answers (scratch-3, flag on, 2026-09-30, small n)

The data is in `logs/relay2/runs/scratch3-L5-relaymodes.json` (n=12, 1 edit per burst) and `scratch3-L5-all-b3.json` (n=12, bursts of 3 edits 20 ms apart, offline probe), plus B6 in `logs/relay2/runs/scratch3-B6-relay.json`. The full-n reruns go into `results/relay2/raw/`.

**Envelope beside the provider's own sends: reliable.**
- Pairing hits and misses:
  - relay mode, 1-edit bursts: 12 hits, 0 misses.
  - relay mode, 3-edit bursts: 37 hits (36 update + 1 step2), 0 misses.
  - relay250 mode, 3-edit bursts merged: 13 hits, 0 misses.
- Zero echo digest mismatches, zero out-of-order echoes (echoes arrive in send order), zero origin commits without a `clientFrameId`, zero rejects.
- Every envelope's `contentHash` was accepted (`contentHashAccepted: true`, 62/62). That means the SV-after-apply computed from the provider's doc at send time matched the server's merged SV every time.
- No interleaving is possible because envelope and frame go out in one synchronous section, or in one queue step when persisting before send, on one ordered WebSocket.

**Provider-internal step2 frames.**
- *Initial sync.* The provider's step2 reply to the server's step1 on first connect left before the harness registered the body, so it went envelope-less. The server handled it as protocol §4.1 says: appended if non-empty, `hashUnknown`, no echo. An empty `[0,0]` step2 is skipped by the server (`emptySkips`), and the wrapper never envelopes it.
- *Offline edits.* The body socket was terminated and 3 edits were made while it was closed. The provider does not queue those frames. On VaultSync's automatic reconnect, the offline edits travelled in the provider's step2 reply.
  - **Enveloped:** the step2 paired, was appended once, `contentHashAccepted: true`, and was settled from the echo. Edit → settled took 368–629 ms, including reconnect.
  - **Without an envelope** (`envelopeStep2=false`, which is what the provider does if nothing wraps it): the server appended it (`appends +1`) with `hashUnknown +1`, and there was no echo or receipt. A client that does not envelope step2 must fall back to HTTP for the offline window. So the integration **must** envelope non-empty step2, not only updates.

**Lost ack / dedupe (B6, relay adapter).**
- The same envelope + frame was sent 3× on the socket, then once more after a reconnect. Result: `appends +1` and `dedupeHits +3`. Every resend got `BODY_COMMITTED deduped:true` with the same `vaultSequence`/`durableGeneration`/`candidateId`/`candidateDigest`.
- A reused `candidateId` with different bytes got `BODY_UPDATE_REJECTED {reason:"candidate_id_reused"}`. It was not appended, not fanned out, and the socket stayed open. Resending it under a fresh id recovers.
- **Cross-path:**
  - Socket commit, then an HTTP `POST /candidate` with the same id + digest → 200 with the same `durableGeneration` (shared `vault_candidate_receipts`).
  - HTTP first, then the socket with the same id → `deduped:true` echo with the HTTP receipt's generation, and no socket append.
  - So the HTTP fallback is safe in both directions.

**Latency (edit applied → candidate settled, p50 after discarding 10 warm-ups; small n, not the RFC number):**

| Mode | 1 edit/burst | 3 edits/burst (first edit / last edit) |
|---|---|---|
| base prod, HTTP, 250 ms debounce | 531 (scratch-2) | 518 / 476 |
| base nodebounce, HTTP | 277 (scratch-2) | 439 / 397 |
| relay, socket ack, per frame | ~64 | 94 / 51 |
| relay250, socket ack, 250 ms harness debounce | ~468\* | 345 / 301 |

\*This was the first relay250 run, before VaultSync's HTTP path was parked, so its settle included VaultSync's own HTTP candidate. The 3-edit numbers are clean.

**Wire cost per 3-edit burst (p50):**

| | base prod | base nodebounce | relay | relay250 |
|---|---|---|---|---|
| WS frames out | 3 | 3 | 6 (3 envelope + 3 update) | 4 |
| WS bytes out | 106 | 106 | 1633 | 592 |
| HTTP requests | 1 | 2 | 0 | 0 |
| DO request units (HTTP + WS-in/20) | 1.15 | 2.15 | 0.30 | 0.20 |

The envelope costs ~500 B per frame: two UUIDs, three sha256 hex strings, the SV in base64 and the JSON keys. It is text on an already-open socket and adds no requests. If bytes matter, the obvious cut is to drop `candidateDigest` when it equals `payloadDigest` (single frame), or send digests as base64.

## 4. Integration sketch for VaultSync (not done; for the RFC)

1. **Injection point.** Don't wrap the socket. Own the send instead: install the body-session doc `update` observer *before* the provider's (or construct `YSyncProvider` with a hook) so that one piece of code sees each local update and emits the envelope + frame itself. y-partyserver's `_updateHandler` sends unconditionally, and `broadcastMessage` drops frames while the socket is not OPEN. The two ways to take over the send are a provider option that disables `_updateHandler` for local origins, or a subclass that overrides it. `socketReceipts.ts` proves the envelope fields are all derivable at that point.
2. **Candidate = frame.** Capture one candidate per sent frame, or per merged debounce window with the frame being that merged update (as relay250 does). The candidate id, digest and persisted record are then exactly what the envelope names, and `completeCandidateSubmission` can be reused unchanged with a receipt built from `BODY_COMMITTED`. Persist before send keeps the HTTP path's crash guarantee. The cost is the SQLite/IndexedDB put on the send path (put p50 ~0.2 ms in the CLI store here).
3. **Frame-id map.** Keep `clientFrameId → candidateId` per socket. Drop entries on socket close. Unsettled candidates stay in the store and go through the existing `restoreCandidates`/`retryPendingCandidates` HTTP path, or through a socket resend on reconnect, which dedupes to the same receipt (B6).
4. **step2 without an envelope.** The provider's step2 reply after reconnect carries offline edits. Envelope it with a candidate for the step2 inner bytes (verified above), or leave it envelope-less and let the existing HTTP candidate for those edits settle them. That is correct but slower, and the server records `hashUnknown` until the next hashed append. Empty `[0,0]` step2s need nothing.
5. **Echo checks.** Settle only when the echo's `clientFrameId`, `candidateId`, `candidateDigest` and `payloadDigest` all match. Ignore `peer:true` commits. Treat `BODY_UPDATE_REJECTED` and close codes 4409/4403/1013/1009 as "leave pending → HTTP fallback".
